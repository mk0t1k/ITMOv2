# Отчёт по практике 7.2: Поддержка пользователя с помощью AI-инструментов в n8n

## 1. Общая архитектура решения

В рамках практики была спроектирована и реализована автоматизированная система триажа (первичной сортировки), классификации и еженедельной аналитики обращений (GitHub Issues) на базе платформы оркестрации **n8n**.

Система построена по модульному принципу и состоит из трёх взаимосвязанных сценариев и одного внутреннего хранилища данных:

1. **`Workflow 1: Issue Triage`** — основной event-driven сценарий, реагирующий на создание новых Issues через GitHub Webhook, приветствующий новых контрибьюторов и маршрутизирующий задачи по типам.
2. **`Sub-workflow: Issue Classifier`** — переиспользуемый микросервис (подпроцесс) для AI-классификации текста обращения с гарантированным возвратом структурированного JSON.
3. **`Workflow 4: Weekly Issue Stats`** — cron-сценарий еженедельной аналитики, агрегирующий метрики через GitHub REST/Search API, вычисляющий динамику ($\Delta$) относительно прошлой недели, генерирующий AI-саммари и отправляющий HTML-отчёт на электронную почту.
4. **Data Table `weekly_stats`** — встроенная таблица n8n для персистентного хранения срезов статистики по неделям.

## 2. Детальное описание сценариев (Workflows)

### 2.1. Модуль AI-классификации (`Sub-workflow: Issue Classifier`)

Вынесение LLM-логики в отдельный **Sub-workflow** устраняет дублирование промптов и позволяет переиспользовать классификатор в других сценариях (например, при переоткрытии или редактировании Issue).

* **Входной интерфейс (`Execute Workflow Trigger`):** принимает два строковых параметра — `title` (заголовок Issue) и `body` (текст описания).
* **Языковая модель и цепочка (`Basic LLM Chain` + `OpenAI Chat Model`):** используется модель `qwen/qwen3.7-flash` с few-shot промптом, содержащим чёткие критерии и примеры для 4 категорий:
  * `bug` — сообщение об ошибке, сбое, исключении;
  * `task` — вопрос по использованию, настройке, запуску или документации;
  * `feature` — запрос на добавление новой функциональности;
  * `unknown` — слишком короткое или расплывчатое описание без конкретики.
* **Контроль формата (`Structured Output Parser`):** гарантирует строгую JSON-схему ответа модели (`{ "type": "string", "confidence": "number" }`), исключая необходимость ручного парсинга текста регулярными выражениями.
* **Выходной интерфейс (`Edit Fields / Set`):** возвращает в родительский сценарий плоский объект со свойствами `type` и `confidence` (число от `0` до `1`).

### 2.2. Основной сценарий обработки обращений (`Workflow 1: Issue Triage`)

Сценарий работает в реальном времени и обрабатывает жизненный цикл нового обращения:

1. **Триггер и фильтрация событий (`Github Trigger` + `If`):**
   * Вебхук подписан на событие `issues`.
   * Нода `If` проверяет строгое условие `{{ $json.body.action }} == "opened"`. Это критически важно, так как GitHub присылает вебхуки на любое изменение Issue (`labeled`, `edited`, `closed`), при которых статус `state` остаётся `"open"`. Фильтрация по `action == "opened"` предотвращает бесконечные циклы при навешивании лейблов самим ботом.
2. **Обработка новых участников (`If: First-time contributor`):**
   * Проверяется встроенное поле GitHub payload `author_association == "NONE"` (означает, что пользователь ранее не делал коммитов и не открывал PR в этом репозитории).
   * Если условие истинно, через GitHub API добавляется лейбл `first-time-contributor` и публикуется приветственный комментарий с упоминанием автора (`@login`) и ссылкой на `CONTRIBUTING.md`.
3. **Вызов классификатора (`Execute Workflow`):**
   * Передаёт `issue.title` и `issue.body` в `Sub-workflow: Issue Classifier` и дожидается возврата `type` и `confidence`.
4. **Маршрутизация и эскалация (`Switch`):**
   * **Ветка 0 — Эскалация (`unknown` / низкая уверенность):** срабатывает первой, если `confidence < 0.8` **ИЛИ** `type == "unknown"`. На Issue вешается лейбл `needs-triage`, а **комментарий не публикуется**, чтобы не давать пользователю нерелевантный автоответ и передать обращение человеку-мейнтейнеру.
   * **Ветки 1–3 (`bug`, `task`, `feature`):** если `confidence >= 0.8`, проставляется соответствующий лейбл (`bug`, `task` или `feature`) и публикуется шаблонный комментарий, подтверждающий принятие обращения в работу.

### 2.3. Сценарий еженедельной аналитики (`Workflow 4: Weekly Issue Stats`)

Сценарий формирует управленческую сводку по состоянию репозитория:

1. **Планировщик (`Schedule Trigger`):** настроен на запуск каждый понедельник в 09:00 по cron-выражению `0 9 * * MON`.
2. **Сбор данных через GitHub API (4 параллельных `HTTP Request`):**
   * *Запрос 1 (Активные за неделю):* `GET /repos/{owner}/{repo}/issues?state=all&since={{ $now.minus({ days: 7 }).toISO() }}&per_page=100` — получает все Issues, созданные или обновлённые за последние 7 дней.
   * *Запрос 2 (Закрытые за неделю):* `GET /search/issues?q=repo:{owner}/{repo}+is:issue+closed:>={{ $now.minus({ days: 7 }).toISODate() }}` — возвращает `total_count` закрытых за неделю задач.
   * *Запрос 3 (Открытый бэклог):* `GET /search/issues?q=repo:{owner}/{repo}+is:issue+is:open` — текущее количество открытых Issues.
   * *Запрос 4 (Очередь эскалации):* `GET /search/issues?q=repo:{owner}/{repo}+is:issue+label:needs-triage+is:open` — количество неразобранных задач с лейблом `needs-triage`.
3. **Агрегация и очистка данных (`Code node 1`):**
   * В REST API GitHub эндпоинт `/issues` возвращает также Pull Requests, поэтому в JS-коде выполняется фильтрация `!item.pull_request`.
   * Параметр `since` возвращает в том числе старые Issues, которые просто обновились за неделю — код дополнительно фильтрует записи по `new Date(item.created_at) >= weekAgo`.
   * Производится группировка новых Issues по типу лейбла (`byType`: `bug`, `task`, `feature`, `needs-triage`) и по логину автора (`byAuthor`).
4. **Хранение истории и расчёт динамики $\Delta$ (`Data Table` + `Code node 2`):**
   * Сначала из таблицы `weekly_stats` считывается запись за предыдущую неделю (`Get Many`).
   * В `Code node 2` вычисляется разница $\Delta = \text{Current} - \text{Previous}$ по каждой метрике с форматированием знака (`+N`, `-N`, `0`).
   * После расчёта текущие метрики записываются новой строкой в `weekly_stats` (`Insert`).
5. **AI-аннотация недели (`Basic LLM Chain`):**
   * LLM получает JSON с метриками текущей недели и рассчитанными изменениями $\Delta$, после чего генерирует краткий аналитический вывод (3–4 предложения) о трендах по багам и скорости разбора очереди.
6. **Формирование и доставка отчёта (`Send Email`):**
   * Вместо Gmail API использован универсальный протокол SMTP (`n8n-nodes-base.emailSend`) с авторизацией по паролю приложения.
   * Отправляется HTML-письмо, содержащее сводную таблицу с колонками *«Метрика»*, *«За эту неделю»*, *«Δ к прошлой неделе»*, статистику по авторам и выделенный блок **«AI-комментарий недели»**.

## 3. Шпаргалка для защиты (ответы на вопросы ревьювера)

Ниже приведены готовые тезисы по каждому пункту из чек-листа проверки:

1. **Как классификатор возвращает `type` и `confidence` и как `Switch` выбирает ветку?**
   * В `Sub-workflow` связка `Basic LLM Chain` + `Structured Output Parser` принудительно приводит ответ LLM к JSON-схеме с полями `type` (строка) и `confidence` (число с плавающей точкой).
   * В основном сценарии нода `Switch` проверяет правила строго сверху вниз: **первым правилом** стоит проверка порога уверенности `confidence < 0.8 OR type == "unknown"`. Только если модель уверена в ответе ($\ge 0.8$), срабатывают последующие правила для `bug`, `task` или `feature`.

2. **Почему Issue попал в `needs-triage` и почему на него нет комментария?**
   * Когда описание обращения слишком короткое или неоднозначное (например, *«Не работает, помогите»*), LLM выставляет низкий `confidence` ($< 0.8$) или тип `unknown`.
   * `Switch` направляет такой Issue в ветку эскалации: вешается лейбл `needs-triage` для привлечения мейнтейнера. Комментарий не публикуется намеренно, чтобы бот не вводил пользователя в заблуждение ошибочным шаблоном при низкой уверенности классификации.

3. **Как основной сценарий вызывает `Sub-workflow` и что передаётся между ними?**
   * Используется нода `Execute Workflow`, которая ссылается на опубликованный `Sub-workflow: Issue Classifier`.
   * Из основного сценария на вход триггера подпроцесса передаются только очищенные текстовые поля `title` (`body.issue.title`) и `body` (`body.issue.body`). Подпроцесс изолирован от контекста GitHub и возвращает обратно только два поля: `type` и `confidence`.

4. **Какие запросы к GitHub API собирают статистику и как `Code node` её группирует?**
   * Используются 4 GET-запроса: 1 запрос к REST API (`/repos/.../issues?state=all&since=...`) для получения списка всех затронутых за неделю задач и 3 запроса к Search API (`/search/issues?q=...`) для точного подсчёта `total_count` по закрытым за неделю, всем открытым и открытым с лейблом `needs-triage`.
   * В `Code node` из первого запроса отсеиваются Pull Requests (`!item.pull_request`) и задачи, созданные раньше 7 дней назад (`created_at >= weekAgo`), после чего в цикле подсчитываются счётчики в словарях `byType` (по массиву `issue.labels`) и `byAuthor` (по полю `issue.user.login`).

5. **Откуда берутся данные прошлой недели и на основе чего LLM пишет аннотацию?**
   * Данные прошлой недели считываются из встроенной таблицы `Data Table` (`weekly_stats`) **до** записи туда результатов текущей недели.
   * `Code node` вычисляет разницу $\Delta$ между текущими показателями и последней строкой из `Data Table`. Затем оба объекта (`current` и `delta`) передаются в промпт `Basic LLM Chain`, на основе которых модель формулирует текстовый вывод для блока «AI-комментарий недели».
